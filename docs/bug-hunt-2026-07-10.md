### BUG-1 [high, conf=high] 반복(rrule) 일정이 서버 range/month 조회에서 발생 인스턴스로 전개되지 않고 마스터 1건만 반환됨
- 파일: `/Users/hyunseokbyun/hyun-hub/service/domain/calendar/calendar.ts` 409-412 (range), 221-224 (month)
- 설명: getEventsByDateRange(및 getEventsByMonth)에서 rrule 이벤트에 대해 getRecurrenceOccurrences(...)로 실제 발생일 배열을 계산하지만, 그 결과(occurrences)의 날짜를 전혀 사용하지 않고 `if (occurrences.length > 0) result.push(event)` 로 원본 마스터 이벤트(원래 dtstart 그대로)만 1건 push 한다. 즉 반복 일정이 각 발생일마다 렌더되지 않고, 마스터의 dtstart 위치에 단 한 번만 나타난다. 더 심각하게는, 조회 범위에 발생일은 있으나 마스터 dtstart 가 범위 밖(이전 달)인 경우 반환된 이벤트의 startDate 가 화면 주(week) 범위 밖이라 클라이언트 computeWeekLayouts 필터에서 제거되어 반복 일정이 아예 보이지 않는다. 이미 알려진 (b) 클라이언트 매퍼 rrule 소실과 별개의, 더 근본적인 서버측 결함이며 (b)를 고쳐도 이 문제로 반복 일정은 정상 렌더되지 않는다.
- 재현: 주간 반복 all-day 이벤트를 6/1 시작으로 생성 → 8월을 조회. 8월 range 응답에는 (a) 마스터 1건만, dtstart=6/1 로 반환됨 → 클라이언트 8월 그리드 주 범위(7/26~9/5 등)에 6/1 이 없어 필터링 → 8월 화면에 반복 일정이 하나도 표시되지 않음. 시작 달(6월)에서도 6/1 한 칸에만 표시되고 나머지 주간 발생일은 누락.
- 제안 수정: rrule 분기에서 occurrences 각 날짜별로 dtstart/dtend 를 해당 발생일로 이동(기존 duration 보존)한 CalendarEvent 를 생성해 result 에 push 하도록 변경(서버측 전개). month/range 두 경로 모두 동일 수정. 서버 전개로 통일하면 클라이언트는 rrule 을 몰라도 됨.

### BUG-2 [high, conf=high] 날짜범위 조회가 overlap 이 아니라 dtstart-in-range 로 필터해, 범위 시작 이전에 시작한 다일/종일 이벤트가 누락됨
- 파일: `/Users/hyunseokbyun/hyun-hub/compose/calendar.ts` 26-41 (SQL), service .../calendar.ts:405 및 217
- 설명: DB 쿼리(getEventsByDateRange/getEventsByMonthRange)의 비반복 조건이 `dtstart >= startDate AND dtstart <= endDate` 로, 이벤트 '시작일'이 범위 안에 있어야만 반환한다. 서비스 계층(calendar.ts:405, 217)도 동일하게 `event.dtstart >= startDate && event.dtstart <= endDate` 로 다시 필터한다. 올바른 겹침(overlap) 조건은 `dtstart <= endDate AND dtend >= startDate` 여야 한다. 결과적으로 '범위 시작일보다 먼저 시작했지만 범위 안으로 이어지는' 다일/종일 이벤트가 조회에서 통째로 빠진다. 클라이언트 range startDate 는 startOf('month').startOf('week') (예: 7월 조회 시 6/28)이므로, 6/28 이전 시작 이벤트가 실제 7월 날짜까지 걸쳐 있어도 7월 화면에서 사라진다.
- 재현: 6/15~7/10 종일 이벤트 생성 → 7월 조회(range startDate≈6/28). dtstart(6/15) < 6/28 이라 DB/서비스 필터에서 제외 → 7/1~7/10 셀(실제 7월 날짜)에 이벤트가 렌더되지 않음. 6월을 보면 정상 표시되므로 '달을 넘기면 사라지는' 증상.
- 제안 수정: DB where 절의 비반복 조건을 overlap 조건 `and(lte(dtstart, endDate), gte(dtend, startDate))` 로 변경하고, 서비스 계층의 `event.dtstart >= startDate` 재필터도 overlap(dtstart<=end && dtend>=start) 기준으로 수정하거나 제거한다.

### BUG-3 [medium, conf=high] 클라이언트 조회 범위(endDate)가 항상 6주 렌더 그리드보다 짧아, 그리드 후행 주의 이벤트가 미조회로 누락됨
- 파일: `/Users/hyunseokbyun/bcalendar/widgets/calendar/calendar-widget.tsx` 36 (endDate), page.tsx:14, calendar-utils.ts:15-32
- 설명: 그리드는 getMonthDays 가 WEEKS_IN_GRID(=6)주(42일)를 무조건 렌더한다(calendar-utils.ts:22, constant/calendar.ts:1). 그러나 조회 범위 endDate 는 `dayjs(currentMonth).endOf('month').endOf('week')` 로 계산되어 달이 4~5주만 차지하면 28/35일까지만 조회한다(SSR page.tsx:14, 위젯 calendar-widget.tsx:36 동일). 시작(startOf('month').startOf('week'))은 그리드와 같지만 끝이 짧아, 렌더되는 5~6주차(다음 달 앞부분, 회색 셀)의 이벤트가 fetch 되지 않아 표시되지 않는다. 스크립트로 검증: 2026-02 조회 시 query end=2026-02-28 vs grid end=2026-03-14 로 2주 미조회. 2026-03 은 query end=2026-04-04 vs grid end=2026-04-11.
- 재현: 2026년 2월을 조회(그리드는 3/14까지 렌더). 3/5 에 일정 생성 후 2월 화면을 보면 3/5 셀은 그리드에 보이지만 조회 범위(2/28) 밖이라 일정이 표시되지 않음.
- 제안 수정: 조회 endDate 를 그리드와 동일하게 `startOf('month').startOf('week').add(WEEKS_IN_GRID*7 - 1,'day')` 로 계산(page.tsx·calendar-widget.tsx 동일 적용)하거나, getMonthDays 를 가변 주수로 만들어 그리드와 조회 범위를 단일 소스로 정렬한다.

### BUG-5 [medium, conf=medium] '+N 더보기' 드로어가 그룹 가시성을 무시해 숨긴 그룹의 이벤트까지 노출하고 개수 라벨과 내용이 불일치
- 파일: `/Users/hyunseokbyun/bcalendar/features/calendar/calendar-grid.tsx` 322-324
- 설명: '+N 더보기' 클릭 핸들러가 `events.filter((ev) => ev.startDate <= dateStr && ev.endDate >= dateStr)` 로 전체 events(=useCalendar 의 원본 목록, 숨긴 그룹 포함)를 필터한다. 반면 오버플로 개수 라벨 locale.more(overflow.length) 와 그리드 렌더는 visibleEvents(가시 그룹만)로 계산된다(use-calendar.ts:74-79, computeWeekLayouts). 따라서 (1) 사이드바에서 숨긴 그룹의 이벤트가 드로어에 그대로 나타나고, (2) '+2' 라벨과 드로어에 뜨는 실제 건수가 어긋난다. 참고로 CalendarCell 은 onShowMore/overflowEvents props 를 받지만 사용하지 않는 dead prop 이라(calendar-cell.tsx:19) 이 그리드측 핸들러가 유일 경로다.
- 재현: 그룹 A 를 숨김 → 특정 날짜에 오버플로가 생기도록 가시 이벤트 4건+ 및 숨긴 그룹 A 의 이벤트 1건 배치 → '+N 더보기' 클릭 → 드로어에 숨긴 그룹 A 이벤트가 표시됨(가시 그리드에는 없음).
- 제안 수정: 핸들러에서 가시 그룹만 남기도록 필터(visibleEvents 기준)하고, 라벨 개수와 드로어 내용이 일치하도록 동일 소스를 사용한다.

### BUG-6 [low, conf=low] updateEventAction 이 isAllDay 미포함 부분 PATCH 시 isAllDay 를 false 로 가정해 종일 endDate exclusive 변환이 누락될 수 있음(잠재)
- 파일: `/Users/hyunseokbyun/bcalendar/entities/calendar/api.ts` 104-107
- 설명: updateEventAction 에서 `const isAllDay = rest.isAllDay ?? false` 후 `endDate: rest.endDate ? (isAllDay ? toExclusiveEndDate(rest.endDate) : rest.endDate) : undefined`. endDate 를 포함하되 isAllDay 를 생략한 부분 업데이트가 발생하면, 실제로 종일 이벤트여도 isAllDay=false 로 간주되어 inclusive→exclusive(+1일) 변환이 누락되어 서버에 하루 짧은 종일 endDate 가 전달된다. 현재 endDate 를 갱신하는 모든 호출 경로(DnD move/resize, 폼, 편집 팝오버)는 isAllDay 를 함께 보내므로 재현되지 않는 잠재 결함이나, 방어적으로 위험하다.
- 재현: 현재 호출부에서는 미발생. 향후 `{ endDate }` 만 담아 updateEvent 를 호출하는 경로가 추가되면 종일 이벤트 종료일이 하루 당겨져 저장됨.
- 제안 수정: isAllDay 기본값을 false 로 가정하지 말고, endDate 변환 판단에 필요한 isAllDay 를 항상 함께 전달받도록 계약을 고정하거나, 대상 이벤트의 isAllDay 를 조회해 사용한다.

### BUG-7 [low, conf=low] data 기본값 = initialEvents 폴백이 모든 달 쿼리에 적용되어 월 이동 로딩 중 로딩 표시가 없고 초기 달 데이터로 폴백
- 파일: `/Users/hyunseokbyun/bcalendar/widgets/calendar/calendar-widget.tsx` 38

## 비고

- 가설검증으로 기각한 항목(과대보고 방지): (1) getMonthDays 의 dayjs `.month()` 데이-오버플로 버그 없음 — 프로젝트 dayjs 는 `dayjs('2026-01-31').month(1)` → 2026-02-28 로 clamp(네이티브 setMonth 의 3월 롤오버와 다름). (2) computeWeekLayouts 오버플로 bump 중복 카운트 가설 — 다일 이벤트를 마지막 가시 레인에 배치한 실측 시나리오에서 중복 미발생하여 리포트 제외.
- 이미 알려진 (a) 드래그 groupId 소실의 근본 원인 위치 확인: bcalendar entities/calendar/api.ts:108 `groupId: rest.groupId || null`. 서버는 PATCH 바디에 groupId 미포함 시 기존값 보존(event.ts:200, mapper:103)하나, 클라이언트가 부분 업데이트에도 항상 groupId 를 null 로 강제 전송하여 DnD move/resize 시 그룹이 지워짐. (별도 수정 중이라 하여 상세 생략)
- 알려진 (b) 확인: bcalendar types.ts:176-189 toCalendarEvent 가 rrule/exdate/priority/transp/categories 를 매핑하지 않아 소실. 단 BUG-1 서버 미전개가 더 근본 원인이라 (b) 단독 수정으론 반복 일정이 정상화되지 않음.
- 알려진 (c) 확인: getEventDetailAction(api.ts:71)·API_PATH.EVENTS.DETAIL 는 어느 클라이언트 컴포넌트에서도 호출되지 않는 dead code.
- 알려진 (d) 종일 exclusive/inclusive 경계: 생성(api.ts:83 toExclusiveEndDate)·조회(api.ts:16 toInclusiveEndDate)로 왕복 일관. 정상 경로는 round-trip 유지되나 BUG-6 의 잠재 경로에서 깨질 수 있음.
- 시간대: 서버 combineDatetime 이 timed 이벤트 시각을 `T{time}:00Z`(UTC)로 저장하고 formatTime 도 getUTCHours 로 되읽어 왕복 일관하나 timezone-naive(floating). 종일 이벤트는 전 구간 문자열 'YYYY-MM-DD' 로만 다뤄 tz drift 없음. 현재는 버그 아님(설계 단순화)로 판단.
- 컨벤션 관측(버그 아님, 참고): query.ts 의 QueryClient/Provider 에 기본 staleTime 60초 미설정으로 보임(query-provider 확인 필요). useCalendarEvents 에 staleTime/placeholderData 부재는 BUG-7 과 연관.
- calendar-utils diff('day') 는 DST 전환 주에 컬럼 오프바이원 가능성이 이론상 있으나(dayjs day-diff 는 DST 미보정), UTC/floating 처리와 한국(DST 없음) 기준에선 재현 어려워 low 로도 리포트하지 않음.
